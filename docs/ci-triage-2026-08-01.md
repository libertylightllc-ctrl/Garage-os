## Finding 1 — mock-key omission (single suite)

One `vi.mock("@/lib/prisma")` fixture (in
`src/app/actions/__tests__/techfindings-empty-desc.test.ts`) listed
`jobCard`, `part`, and `jobPart` but did not list `user`. When
`sessionUserExists` landed and started calling `prisma.user.count(...)`
from inside `requireAnyRole`, every test in that suite crashed with

    TypeError: Cannot read properties of undefined (reading 'count')
    at src/lib/session-user.ts:28

The failure reads as a runtime crash rather than a mock gap, which is
why it survived 91-plus commits: nothing in the message says "your
mock is missing a model".

Two sibling suites — `session-user-guard.test.ts` and
`ai-event-log.test.ts` — also mock `@/lib/prisma`. They happened to
survive because their mocks either included every model the code path
uses (`user.count`) or exercised a code path that never called
`requireAnyRole`. That's coincidence, not design.

**Fix landed:** commit `540d9db` — added
`user: { count: () => Promise.resolve(1) }` to the mock.

## Finding 2 — fake-session pattern across integration suites

The stronger finding, and the one AR flagged as the real class-of-bug.

Roughly 15 integration test files use `vi.mock("@/auth", () => ({
auth: () => mockAuth() }))` and then feed the mock synthetic session
objects like

    { user: { id: "sup-iso-test-u", role: "OWNER", garageId: gA, ... } }

Before `5e2ed5b4`, `requireAnyRole` only checked the role. Any string
in `id` was fine — nothing in the guard cared whether the id
corresponded to a real User row, so the mocked session sailed through
and the test exercised its intended assertion. After `5e2ed5b4`, the
guard runs `prisma.user.count({ where: { id } })` against a real
Postgres, finds 0, and redirects to `/login`. Every test in every
affected suite fails with the same assertion:

    AssertionError: expected '/login' to be '/owner/…'

**The tests were wrong before the guard commit landed** — they were
asserting against an impossible production state (a valid JWT for a
non-existent user). The guard exposed the gap; it did not create it.

The pattern is 11 files total. After the recovery push:

| Class | Count | Files |
|---|---|---|
| Fixed via `mockSessionAndSeed` (5 CI-recovery commits) | 5 | inventory-isolation, estimate-line-link, partrequest-stock, parts-import-isolation, supplier-isolation |
| Self-seed a matching User row (guard genuinely exercised) | 5 | admin-isolation, owner-intake, role-flows, solo-owner, work-session |
| Anti-pattern — mocks `sessionUserExists` itself to always return true | 1 | purchasing-isolation |

**The remaining loose end:** `purchasing-isolation.test.ts` adopts the
shape AR explicitly rejected on the process-env-bypass proposal —
mocks the guard away so no test in the suite can ever verify that
`sessionUserExists` rejects a stale JWT. CI passes because the guard
is silenced, not because the tests exercise it. Coverage gap; not a
CI regression risk. Convert to `mockSessionAndSeed` when we come back
to it.

## Follow-up 1 — shared mock factory

The mock-key omission would recur the moment `requireAnyRole` (or any
shared guard) starts calling a new model. Three test files today mock
`@/lib/prisma` with a hand-rolled per-file object listing only the
models each suite touches:

- `src/app/actions/__tests__/techfindings-empty-desc.test.ts`
- `src/lib/__tests__/session-user-guard.test.ts`
- `src/lib/__tests__/ai-event-log.test.ts`

A shared factory in `src/lib/__tests__/helpers/mock-prisma.ts` would
export a default mock with every model stubbed to `vi.fn()`, with a
convenience for the caller to override specific methods for its
assertions. Adopting it means "the guard was quietly extended to
touch a new model" can never again break a mock silently — the
factory has that model in its default, and every consuming suite
inherits the fix.

Not urgent, but low-effort. Do it before the next guard change.

## Follow-up 2 — vitest local pool

Local runs on this box hit "Server has closed the connection" under
vitest's parallel forks against the Prisma 7 bundled dev proxy. The
proxy's connection cap is low; the parallel runner exhausts it and
tests cascade into misleading "connection dropped" failures that mask
the real signal. That's what made the local suite unusable and stalled
Layer 0 verification.

Add to `vitest.config.ts`:

```ts
export default defineConfig({
    test: {
        pool: "forks",
        poolOptions: {
            forks: {
                singleFork: true,
            },
        },
    },
});
```

CI is unaffected — its ephemeral `postgres:16` container has a normal
connection limit; parallel forks don't strain it. This is a
local-only knob.
